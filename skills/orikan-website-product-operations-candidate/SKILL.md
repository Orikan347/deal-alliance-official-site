# Orikan Website Product Operations

## 一句話目標

把每一次網站修改都做成「訪客看得懂、機器讀得懂、營運可承接、出問題能回退」的產品改版；不是只把頁面做漂亮，也不是只補 meta。

## 這個 Skill 解決什麼

適用於新網站、改版、增加頁面、工具／課程說明、CTA、資源文章、網域搬遷、公開表單、SEO/GEO 修正、設計一致性、可用性、效能與上線後追蹤。

不取代既有 Skill：

| 工作 | 先走哪個 Skill | 本 Skill 的角色 |
|---|---|---|
| 競品／Raymond／後台研究 | `website-research-backup` | 接收去識別化研究結論，不做未授權操作 |
| GitHub／Cloudflare 部署 | `taixin-website-deployment` 或專案 release contract | 交付已驗收的變更包與回滾點；不自行部署 |
| 成交聯盟桌面產品狀態 | `deal-alliance-product-delivery` | 官網只顯示已核實的公開狀態 |

## 永久準則

1. **先人後機器。** 第一屏先回答「這是什麼、幫誰、下一步是什麼」；SEO/GEO 是讓正確內容被發現，不是關鍵字堆砌。
2. **先事實後設計。** 每個價格、案例、可用狀態、平台、下載、註冊、客服與法律說法都要有公開來源、責任人與最後核對日；沒有就移除或明列待確認。
3. **一個頁面一個決策。** 每頁只能有一個主行動；CTA 必須與服務的真實狀態一致，不能用漂亮按鈕暗示尚未開放的功能。
4. **視覺系統不是裝飾。** 先維護自己的 logo、色票、字級、間距、卡片、按鈕、狀態與影像規則，再做個別頁面；借鑑資訊架構，不複製他人品牌外觀或文案。
5. **無障礙也是 GEO。** 使用語意 HTML、可見標籤、鍵盤焦點、足夠對比、替代文字與可讀的錯誤訊息；這同時幫助螢幕閱讀器、人類、搜尋與回答型 AI。
6. **可見內容與機器資料是同一份承諾。** title、description、canonical、OG、JSON-LD、sitemap、llms.txt 與正文不可互相矛盾；schema 只能寫頁面看得到、已證實的內容。
7. **公開與私有分離。** 登入、帳號、付款、訂單、學生、管理、草稿與測試入口預設 noindex／最小權限；不能為了曝光公開私人資料。
8. **每次都留下回退路。** 改版前有 baseline、改版後有實測、發布前有版本與回滾點；真實送出、付款、發送、下載、帳號動作均需使用者明確核准。
9. **量測不是猜測。** 沒有 Search Console、Bing、分析或訪客測試資料時，只能寫 `PENDING_MEASUREMENT`，不能宣稱流量、轉換或 AI 引用成果。
10. **訪客產品文案與內部狀態分層。** 對外產品介紹只能依品牌使命、經核實的使用者任務、工作與生活利益、實際操作說明與已核准公開案例撰寫；簽章、DMG、staging、測試代號、部署紀錄與工程 Gate 只能留在內部驗收。找不到獨立來源的產品，一律不渲染成公開工具。

## 內容來源分層｜先確認「拿什麼資料說話」

每一個公開訪客看得到的核心主張都要先進 `content_sources` 的來源台帳，並標示核對日。來源分四層，不能混用：

| 層級 | 可寫進公開產品頁的內容 | 不可拿來當產品文案 |
|---|---|---|
| 品牌層 | 創辦人使命、願景、文化價值、方法論 | 未核對的個人經歷、願景推論 |
| 使用者利益層 | 工作困擾、可公開的使用情境、時間與掌握感的利益 | 課程、MBAF、成交地圖、DISC、未公開教材或把課綱當產品承諾 |
| 產品層 | 已核實的使用步驟、輸入／預覽／確認／停止邊界、適用工作 | 想像中的功能、未完成的整合、模擬資料做成真服務 |
| 狀態層 | 簡短且誠實的「是否開放」說明 | DMG、簽章、staging、版本代號、工程測試結果 |

固定順序是：`先讓人點頭的問題（Mini Yes） → 能得到的結果（Benefit） → 為何適合這個工作（Advantage） → 已證實的操作細節（Feature） → 開放狀態與下一步`。不得從功能清單或內部發布狀態開始。

若服務尚未可真實操作，公開頁可以說清楚「目前未開放」與「正式開放前還需要什麼」，但不得放假表單、假下載、假試用、假預覽器或會讓人以為資料已被接收的互動。每次改產品頁，Gate 必須檢查：來源台帳、公開 catalog、可見正文、metadata／schema、sitemap 與產物是否對齊。

## 三輪批判後的結論

### 第一輪：只做視覺好看，為什麼不夠

問題：漂亮 landing page 可能仍讓訪客不知道品牌服務誰、按鈕會做什麼，或把候補誤看成可購買服務。

否決：先選配色、堆 Hero 圖、每頁放多個「立即開始」。

保留：每個頁面先寫 `訪客問題 → 一句答案 → 證據／限制 → 唯一下一步`，再選擇能強化理解的品牌視覺。設計驗收從「好不好看」升級為「五秒是否看懂、能否鍵盤操作、手機能否完成任務」。

### 第二輪：只做 SEO／GEO 清單，為什麼不夠

問題：title、schema、llms.txt 都存在，仍可能把錯誤事實、虛假價格或不可用服務放大；也不能保證排名或被 AI 引用。

否決：關鍵字堆砌、隱藏文字、為 AI 另寫一份內容、空頁 schema、批量薄文章。

保留：以「可引用事實卡」驅動內容。每個核心主題先有直接答案、作者／品牌、日期、來源、範圍、限制、相關頁與自然下一步。把 robots／sitemap／canonical／HTML／schema 視為同一條發現鏈；公開允許回答型 crawler 與是否允許模型訓練要分開決策。

### 第三輪：只靠一次交付，為什麼不夠

問題：網站最常壞在後續小改：CTA 指到舊入口、schema 沒同步、手機版溢出、圖片變慢、舊 claim 沒收回、監控只看首頁。

否決：把規則放在某位設計師或工程師腦中，或只以 build PASS 宣稱完成。

保留：一個總 Skill 加五個模組、固定改版卡、機器檢查與真人瀏覽器驗收；改動越小，仍要走縮小版 Gate。每次從假資料走到底，並保存修改、風險、回滾與待 owner 確認事項。

### 第四輪：規則很完整，為什麼仍可能做不好

這是本專案依前面三輪實作經驗做的**實務歸納**：清單很長，不代表下一位執行者知道哪一項優先，也不代表「畫面沒壞」就是設計變好。

問題有四個：

1. 小小的文案修正與付款／帳號改動若走同一套流程，會不是太慢、就是有人開始跳過 Gate。
2. 「做得有質感」沒有可判斷標準，容易又回到憑個人喜好。
3. 說要看速度、轉換與可發現性，卻沒有改版前後基準，最後只能猜。
4. 頁面沒有 owner、到期日與舊 claim 清理責任，內容會慢慢過期。

否決：通用一份超長 checklist、以 build PASS 代替視覺／訪客驗收、寫死不適用所有網站的效能數字、以「看起來很好」替代決策證據。

保留：每次先分級，再用一張頁面契約鎖定目的；設計用三個可見判準驗收；量測以前後 baseline 和已核准目標為準；每個公開主張都要能追到 owner 與核對日。

## 第四輪落地：分級 Gate、頁面契約與設計判準

### A. 變更分級

| 等級 | 何時使用 | 最小必跑 | 不可省略 |
|---|---|---|---|
| `QUICK` | 無新公開主張的拼字、排版、已核准文案修正 | 目標元素、桌面／手機截圖、斷鏈與 metadata 影響檢查 | 不得偷偷改 CTA、canonical、schema、狀態或資料蒐集 |
| `STANDARD` | 新頁、CTA、資源、導覽、既有功能或公開 claim 變更 | 頁面契約、假資料流程、桌面／手機／鍵盤、SEO/GEO、公開／私有邊界 | 改前後 baseline、回滾點、可見／機器資料一致 |
| `HIGH_RISK` | 帳號、付款、下載、送出、個資、授權、網域／redirect、大量內容遷移 | 完整 STANDARD Gate＋安全／隱私／法務 owner＋預覽＋使用者逐項核准 | 未核准不得啟用、不得以測試 PASS 偽稱正式開放 |

只要碰到公開主張、CTA 目的地、schema、資料欄位、權限或 redirect，即使改動很小，也至少升為 `STANDARD`。

### B. 每頁的不可省略「頁面契約」

開始設計前，要寫清楚：

1. 訪客在 5 秒內應理解的承諾。
2. 此頁唯一的主行動，以及不點時仍能得到的資訊。
3. 支撐承諾的公開證據、owner、核對日與到期／重審日期。
4. 此頁在內容叢集中的上游問題與下游下一步。
5. 可索引、私有或暫不公開的原因。
6. 改版成功的可觀察證據：例如完成流程、理解測試、合法的點擊事件、Search Console／Bing 讀回或 `PENDING_MEASUREMENT`。

缺任何一項時，不能進入視覺製作；先補資料、降級為公開說明，或刪除頁面。

### C. 視覺不是「有質感」：三個可見判準

每個受影響頁在桌面與窄手機都要回答：

| 判準 | 必須看見什麼 | 失敗例子 |
|---|---|---|
| `理解層級` | 第一屏有品牌／問題／答案／主行動的清楚順序 | 大圖很漂亮，但看不出提供什麼或按鈕做什麼 |
| `品牌辨識` | 使用自己的 token、元件、影像與語氣，有一致的記憶點 | 模仿別站配色、字型、版型或每頁各像不同產品 |
| `操作清楚` | 連結、按鈕、狀態、焦點、錯誤、loading 與不可用原因可辨識 | 假按鈕、只靠顏色、手機重疊、按了沒有回應 |

不可只口頭說「好看」。交接至少保留受影響頁的桌面與手機可見證據，以及鍵盤 tab 順序／主 CTA 行為的讀回。

### D. 量測與內容保鮮

- 改動前記錄可取得的 baseline；沒有資料明寫 `NO_BASELINE`，不得編造改善幅度。
- 改動後只對已核准的目標讀回，例如完成率、有效詢問、Search Console 曝光／點擊、已知 referral、Core Web Vitals 或訪客理解測試；以該網站目前 baseline／目標決定門檻，不硬套萬用數字。
- 內容、FAQ、工具狀態、價格、案例、法律頁、CTA 和 resource 都要有 `owner`、`last_reviewed`、`review_due`。逾期或來源失效時，先降級、隱藏或標待確認，不讓過期 claim 繼續被 SEO／GEO 放大。

### 最終設計

不是六個互相重疊的 Skill，而是本總 Skill 調度五個模組：

1. `品牌與設計系統`：資訊層級、色票／字體／間距 token、元件、狀態、行動版與無障礙。
2. `內容與權威`：問題叢集、作者／來源／日期、案例證據、內部連結與資源更新。
3. `SEO／GEO 事實鏈`：索引、metadata、canonical、schema、crawler、AI 可引用答案與跨站實體一致。
4. `技術品質與隱私`：效能、圖片、404／redirect、表單最小化、安全標頭、公開／私有邊界。
5. `發布與營運觀測`：功能測試、真人驗收、監控、回滾、成效讀回與錯誤回流。

## 外站研究轉化｜雷蒙30內容系統保留規則

本節只保存經研究可跨品牌使用的**方法**，不複製雷蒙30的文章、品牌語氣、圖片、會員內容、課程、價格、人物故事或技術堆疊。每一條都必須先轉成成交聯盟／泰欣自己的公開事實與讀者任務。

| 研究後保留的邏輯 | 成交聯盟／泰欣的改造方式 | 不可照搬 |
|---|---|---|
| 真實工作經驗會累積成內容資產 | 每次課程、工具測試、已核准案例或公開高頻問題，都先做一張「內容來源卡」；再選擇文章、資源、FAQ、工具教學或電子報其中最適合的輸出 | 把客戶對話、學生資料、非公開內容或外站文章整批搬上網站 |
| 內容不是孤立貼文，而是問題叢集 | 建立 `問題總頁 → 深度資源／FAQ → 對應工具／課程說明 → 真實下一步` 的內部連結；每個資源至少有一個上游問題頁與一個下游行動 | 為了 SEO 大量做相似薄文、重複導流或假相關連結 |
| 內容與網站是同一條讀者路徑 | 官網負責可查證的品牌、資源與服務狀態；文章、FAQ、工具說明與電子報候選都要連到真正能解決當下問題的公開頁 | 把非公開內容、名單、登入頁或未核准說法納入公開索引 |
| 一篇內容可以被合理再製 | 原始來源先經 owner／公開性確認，再轉成不同深度的文章、短內容、FAQ、課程段落或工具說明；每一版都保留來源、事實核對日與不同讀者目的 | 同文改標題批量發布、用 AI 填滿沒有第一手價值的頁面 |
| AI 負責整理，人負責觀點與責任 | AI 可以協助聚類、整理結構、做 metadata、檢查連結與提出候選；公開主張、案例、價格、承諾、語氣與發布決定由 owner 核准 | 把 AI 自行推論當成品牌事實或使用者見證 |
| 內容飛輪必須可復盤 | 每月檢查「哪個問題帶來閱讀、理解或合格詢問」，再調整問題頁、資源與 CTA；資料不足就標 `PENDING_MEASUREMENT` | 沒有量測或訪客證據就宣稱內容帶來知名度或轉換 |

### 內容飛輪的固定路徑

```text
已核准的真實經驗／高頻問題
  → 內容來源卡（來源、公開性、讀者問題、日期、owner）
  → 官網問題總頁或資源頁（直接答案、證據、限制）
  → 延伸：FAQ／工具說明／電子報候選
  → 讀者回饋與可量測訊號
  → 每月復盤：保留、更新、合併、下架或新增內容
```

內容來源卡缺作者／來源、公開權限、核對日或讀者問題時，不得進公開頁。本 Skill 只處理網站的公開內容、設計、可發現性、品質與回滾；不處理網站以外的營運。

## 必填輸入：網站改版卡

每次先建立 `task-card.template.md` 的一張實例，至少填：

- 目標訪客、他的問題、唯一成功行動、受影響路由。
- 變更等級（`QUICK`／`STANDARD`／`HIGH_RISK`）與分級理由。
- 頁面契約：5 秒承諾、唯一主行動、公開證據、內容叢集位置、索引邊界與完成證據。
- 事實來源／owner／最後核對日；未知欄位要標 `PENDING_OWNER_INPUT`。
- 公開或私有、是否含表單／帳號／付款／下載／外部動作。
- 視覺目的與既有元件／token；不可只說「做得更高級」。
- SEO／GEO 意圖、主問題、canonical、schema 適用性與內部連結。
- 若為內容：內容來源卡、要放在問題叢集的哪一層、可連至電子報或其他已核准公開入口，以及不應公開的資料邊界。
- 假資料測試路徑、風險、回滾版本、需要使用者確認的外部動作。

## 固定工作流程

### 0. 判定階段與權限

先明示目前為以下其中一階段：

- `FUNCTIONAL_TEST_READY`：可在本機／staging 以去識別化資料操作。
- `PENDING_USER_ACCEPTANCE`：功能已測，等待使用者實際走核心流程。
- `PENDING_RELEASE_SECURITY`：等待正式帳號、付款、法律、簽章或外部設定安全驗收。
- `RELEASE_READY`：功能、真人驗收、安全與發布 readback 都已通過。

不把 mock、截圖、編譯通過或本機網址稱為正式完成。沒有權限時只產出候選與測試證據，不部署、不推送、不送資料。

### 1. 先定「訪客任務」再畫畫面

為每頁寫五句：誰來、他要完成什麼、第一屏答案、主 CTA、完成後得到什麼。若答不出來，先補公開事實或刪除頁面，不開始美化。

### 2. 建立或沿用設計系統

- 用色彩 token、字級比例、間距、容器寬度、按鈕、卡片、badge、alert、空狀態與表單錯誤狀態，而非散落的 CSS magic number。
- 每個主 CTA 具備預設、hover、focus、disabled、loading、success/error 的可見差異；連結、按鈕與不可用狀態不得混淆。
- 桌面、窄手機、鍵盤 tab、縮放與長文字都要實測。視覺風格應有自己的品牌記憶點，卻不犧牲掃讀、對比、讀取速度。
- 依「理解層級、品牌辨識、操作清楚」三欄做視覺 review；三欄任一答不出來，不稱為設計完成。

### 3. 寫出可引用、可維護的內容

核心頁採：`直接答案 → 適用對象 → 方法／證據 → 限制／狀態 → 下一步 → 相關內容`。

資源／文章另補作者、發布／更新日、來源、審稿責任人和上次事實核對日。AI 輔助寫作可以使用，但不可批量製造沒有第一手經驗、來源或讀者價值的薄頁。

內容更新要先問「這則內容在問題叢集中取代、補強還是連結哪一頁？」；若答案只是「多發一篇增加流量」，先停下來補讀者問題與可公開的獨特價值。

### 4. SEO／GEO Gate

可索引頁逐一驗證：

- `lang`、一個 H1、唯一 title／description、canonical、OG、可讀 URL、語意標題、alt、內部連結與行動版可讀。
- sitemap、robots 與 404／redirect 對齊；私有頁不得進 sitemap，並保持 noindex／安全控制。
- JSON-LD 與可見內容逐欄一致。寧可少而完整準確，不寫空白、不完整或不真實的 `Product`／`Offer`／`SoftwareApplication`。
- 主題頁先回答使用者問題，列出作者／組織、日期、範圍與限制，並連回可核對的公開來源；`llms.txt` 只能作導覽，不能取代 HTML、robots、sitemap 或內容品質。
- 公開發現性要檢查 crawler／WAF。若希望在 ChatGPT 搜尋中被發現，需另確認公開頁未封鎖 `OAI-SearchBot`；是否封鎖 `GPTBot` 是另一項訓練政策決策。

SEO／GEO 沒有「保證排名／保證引用」承諾。正式發布後才以 Search Console、Bing、referral 與使用者問題驗證成效。

### 5. 技術、隱私與轉換品質 Gate

- 先測訪客完整流程：開頁、理解、點 CTA、輸入／篩選／預覽／取消／錯誤／完成；用去識別化假資料，禁止真的提交。
- 檢查斷鏈、404、頁面速度、圖片尺寸與 loading、layout shift、mobile overflow、鍵盤、焦點、錯誤訊息與分享卡。
- 表單只蒐集必要資料；尚未有 receiver、同意、保存期限、刪除機制與責任人時，改為不可提交的說明或候補，不假裝已收件。
- 對帳號、付款、下載、管理與學生資料，預設 fail closed：不在公開頁傳遞 password、session、token 或客戶資料。

### 6. 發布、讀回與學習

發布前：保存來源、版本、測試與回滾。發布後：以實際公開 URL 做 GET-only 讀回，確認 canonical、headers、crawler assets、CTA、schema、行動版與 root redirect。

每次結束寫四個資產：固定輸入表、輸出模板、驗收清單、自動檢查；任何失敗都依 `錯誤現象 → 根因 → 修正 → 下次防呆 → 應回寫處` 追加候選規則。只有經 owner 核准、實測多次且不與既有 Skill 重疊的規則，才升格到 TaixinMemoryHub 主版本與安裝副本。

## 不能漏掉、但最容易被忽略的事

| 類別 | 最常被漏掉的問題 | 固定防呆 |
|---|---|---|
| 品牌 | 每頁各像不同網站 | token 與元件使用表；禁止頁面私自造樣式 |
| 信任 | 只有自稱、沒有來源 | 作者／組織、日期、可公開證據、限制與修正紀錄 |
| 發現性 | schema 和畫面不一致 | 逐頁內容與 JSON-LD 對照；用 validator 與公開 readback |
| GEO | 只塞 llms.txt 或追 AI 關鍵字 | 直接答案、來源、結構、可抓 HTML、清楚權威關係 |
| 無障礙 | 按鈕靠顏色、圖片只有字 | semantic HTML、焦點、label、alt、對比、鍵盤／手機測試 |
| 轉換 | CTA 多但沒有下一步 | 一頁一決策、真實可用狀態、完成／取消／錯誤訊息 |
| 隱私 | 先做表單再補政策 | 最小資料、同意、保存、刪除與責任人先完成 |
| 維護 | 小改沒有回歸 | 改版卡、baseline、假資料 E2E、crawler／路由／視覺 Gate |
| 聲量 | 只等搜尋排名 | 問題叢集、原創資源、可分享摘要、作者實體與跨站一致連結 |
| 營運 | 只監控首頁 | 公開路由、CTA、根網域轉址、私有標頭、回滾演練與責任人 |

## 最小驗收輸出

每次交接必須有：

1. 修改檔與頁面／元件影響範圍。
2. 以假資料從頭到尾的操作證據，以及桌面／手機／鍵盤至少一輪可見驗收。
3. SEO／GEO 清單：metadata、canonical、schema、sitemap／robots、公開／私有邊界和仍待外部驗證事項。
4. 已知風險、待 owner 資料、未執行外部動作與明確回滾方式。
5. 變更等級、頁面契約、桌面／手機可見證據、baseline／`NO_BASELINE` 與改後讀回。
6. 本輪是否產生可升格的規則：`NO_RULE_CHANGE`、`CANDIDATE_RULE` 或 `APPROVED_HUB_UPDATE`。
